**Ticket:** [#103](https://github.com/pyrycode/pyrycode-relay/issues/103) · **Size:** XS · **Type:** test-only refactor, no behavior change · **Security-sensitive:** no

## Files to read first

- `internal/relay/ratelimit_test.go` — the only file changed. The 4 SA4000 sites are lines **65**, **83**, **98**, **167** — each is `if !l.Allow("a") || !l.Allow("a") {`. Read the surrounding functions to get the per-site variable names right (see § Design).

The behavioral fact that makes these false positives: `Allow` decrements the token bucket on each call, so two textually-identical calls are *not* redundant. You do not edit this file; read it only to confirm the side effect.
- `internal/relay/ratelimit.go:50` — `NewIPRateLimiter(refillEvery, burst, evictionInterval)`, for context on how the tests construct limiters. No edit.

## Context

`staticcheck ./...` reports 4 SA4000 hits ("identical expressions on the left and right side of the `||` operator") at the four lines above. All four are the same shape:

```go
if !l.Allow("a") || !l.Allow("a") {
    t.Fatal("burst Allows: got false, want true")
}
```

The two `l.Allow("a")` operands look identical to staticcheck's AST check, but `Allow` mutates the bucket (decrements a token) on each call (`ratelimit.go:67`). staticcheck cannot model side effects, so it flags both clauses as redundant. **False positive, not a bug.** Clearing it unblocks adding `staticcheck ./...` to `make check` later (out of scope here; tracked separately per the ticket).

Per the ticket, the fix is **sequential binding** — bind each call to a named variable before the boolean test — not a `//lint:ignore SA4000` suppression. Structural, not suppressive: it makes the two-call sequence explicit and avoids a global-rule waiver.

## Design

At each of the 4 sites, replace the single `if` with two assignments followed by the boolean test over the bound variables:

```go
x1 := l.Allow("a")
x2 := l.Allow("a")
if !x1 || !x2 {
    t.Fatal("…")   // keep the existing message verbatim
}
```

Two sequential `Allow` calls, both must return `true` — identical behavior, distinct operands, no SA4000.

### Per-site variable names (load-bearing detail)

Sites **65** and **83** are both inside the same function, `TestIPRateLimiter_RefillAfterAdvance`, at the same block scope. Reusing one name pair at both — e.g. the ticket's literal `a1`/`a2` — is a **compile error** (`no new variables on left side of :=`, since the second `:=` redeclares names already in scope). Use distinct, context-meaningful names per site:

| Line | Function | Existing comment / intent | Suggested names |
|------|----------|---------------------------|-----------------|
| 65 | `TestIPRateLimiter_RefillAfterAdvance` | "Exhaust the burst at t=0" | `burst1`, `burst2` |
| 83 | `TestIPRateLimiter_RefillAfterAdvance` | "two Allows after 2s advance … (burst cap)" | `refill1`, `refill2` |
| 98 | `TestIPRateLimiter_FractionalRefillPreserved` | "burst Allows" | `burst1`, `burst2` |
| 167 | `TestIPRateLimiter_EvictionPreservesActiveBucket` | "Exhaust the burst" | `burst1`, `burst2` |

Names at 98 and 167 may freely reuse `burst1`/`burst2` because each is in its own function scope; only the 65/83 pair shares a scope and must differ. The names above are a recommendation — any distinct, descriptive pair works. Keep each `t.Fatal` message byte-for-byte unchanged.
