# Ticket #152 — tell the binary when a phone's connection ends

Before this ticket, a phone WebSocket ending was invisible to the binary that served it: the relay logged `phone_unregistered` and moved on, so the daemon kept that phone's v2 session open until its own 15-minute idle sweep, and skipped the device for push wakes (pyrycode/pyrycode-mobile#955). The protocol spec already defined a relay→binary close notice for this; this ticket is the relay-side send.

## Implementation

- **`internal/relay/envelope.go`** — new unexported `marshalCloseNotice(connID string, code uint16) ([]byte, error)`, a standalone `{conn_id, close_code}` struct, deliberately not `Envelope{ConnID: connID}` — `Envelope.Frame` has no `omitempty`, so marshalling a frameless `Envelope` would emit `"frame":null`, not the spec's shape. Returns `ErrEmptyConnID` on an empty id (unreachable in production).
- **`internal/relay/client_endpoint.go`** — `phoneCloseCode(err error) uint16` derives the notice's close code from `StartPhoneForwarder`'s return error: `websocket.CloseStatus(err)` when valid and non-zero, else `1001` (`StatusGoingAway`). `ClientHandler` snapshots `reg.BinaryFor(serverID)` right after registration; once the forwarder returns, `notifyPhoneClosed` sends the notice only if the phone's close was not binary-requested (`!phone.closedByBinary()`) and `reg.BinaryFor(serverID)` still returns the *same* `Conn` (interface identity) as the snapshot. Runs on the phone's own handler goroutine, before the teardown `defer`, so it lands after the phone's last routed frame and before `phone_unregistered`. Send/marshal failure logs `phone_close_notice_send_failed` (`server_id`, `conn_id`, `close_code`, `err` — all pre-existing allowlisted keys, confirmed against `internal/relay/log_allowlist.go`; no new log key).
- **`internal/relay/phone_outbox.go`** — `phoneOutbox` gains `closeRequested atomic.Bool` and `closedByBinary() bool`. `Enqueue` sets it whenever `closeCode != 0` and the outbox is still live, whether or not the directive is ever delivered (i.e. even on overflow) — every production close directive reaches a phone through `Enqueue`, so this one flag is a complete record of "did the binary ask for this."
- **`internal/relay/registry_test.go`** — `fakeConn.Send` now takes its mutex, so tests where phone handlers send to a seeded binary (this ticket's tests) stay race-free.

## Acceptance criteria — verification map

- **AC1** (a phone that ends its own connection produces exactly one envelope naming its `conn_id` with a non-zero `close_code` and no frame, delivered to the binary serving that server-id): `TestClientEndpoint_PhoneClose_NotifiesBinary` (close code echoed) and `TestClientEndpoint_PhoneDrop_NotifiesBinaryGoingAway` (abrupt drop → `1001`), both asserting the decoded notice has no `frame` key.
- **AC2** (a phone closed at the binary's own request produces no such envelope): `TestClientEndpoint_BinaryRequestedClose_NoNotice` — `Enqueue(nil, 4401)` on the registered phone; phone observes `4401` and unregisters; binary receives nothing.

Plus one test beyond the two ACs, added per the architect's design for "skip it when the binary is gone": `TestClientEndpoint_BinaryReplaced_NoNotice` — a second binary claims the server-id before the phone closes; neither binary receives a notice.

## Patterns established

- **Identity comparison, not presence, for "is this still the same peer."** `reg.BinaryFor(serverID)` returning *something* isn't enough to address a notice to it — the handler compares the returned `Conn` against a snapshot taken at registration time. A server-id occupied by a *different* binary (grace-reclaim, conflict-probe takeover) fails the identity check even though the map lookup succeeds. Worth reusing anywhere a handler needs to tell "the same peer is still here" apart from "a peer happens to be here."
- **One `atomic.Bool` as a complete record, when there's exactly one write path.** `closeRequested` doesn't need a full audit trail because `Enqueue` is the only place a production close directive reaches a phone — a single flag set at the one write site is provably complete, not just probably. The same reasoning that already justified `atomic.Bool`/no-lock elsewhere in this type (see [phone-outbox.md § Concurrency model](../features/phone-outbox.md)) extends cleanly to a second field.

## Lessons learned

- The open question from the architecture spec ("do any existing tests with a real binary reader count frames after a phone closes?") resolved clean: no test does, so the new notice couldn't silently break an existing frame-count assertion. The one test that reads binary-received frames closely (`TestRun_ReclaimDuringGraceClosesPhoneWith4404`) asserts on the reclaiming binary's *first* frame being the new phone's probe — it would have caught a stray notice landing ahead of it, and didn't need to change.
- The new tests wait for the handler's `phone_unregistered` log line (via the existing `captureLogger` test helper) rather than polling the registry for the phone's removal. That distinction matters here specifically because a *reclaim* evicts a phone from the registry before its handler goroutine has even run — so "phone gone from registry" and "phone's close-notice decision has been made" are two different moments, and only the log line marks the second one.
