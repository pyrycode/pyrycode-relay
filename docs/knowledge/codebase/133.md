# Ticket #133 — Send an FCM wake when the binary asks for one

Wires the daemon's `push_wake` routing envelope to the FCM sender #132
shipped but never called. `Unmarshal` now recognises the envelope
(`conn_id` absent, `push_wake` present); `parsePushWake` validates it
structurally; `StartBinaryForwarder` hands it to a new `PushWaker`
(`internal/relay/push_wake.go`), which sends through `FCMSender` on its own
goroutine — so a blocking send never stalls the binary read loop — under a
per-server-id rate limit and a relay-wide in-flight cap. `main` builds the
waker from `PYRYCODE_RELAY_FCM_CREDENTIALS`, or logs once that push is off.
Split from #130; blocked by (and follows) #132.

See [Push wake dispatch](../features/push-wake-dispatch.md) for the full
design, [ADR-0013](../decisions/0013-push-wake-async-dispatch-bounded-not-verified.md)
for the accept-the-trust-gap-bound-the-limits decision, and the updated
[Routing envelope](../features/routing-envelope.md) /
[Binary-side frame forwarder](../features/binary-forwarder.md) docs for how
the envelope and the forwarder change.

## Implementation

- Five production files: `internal/relay/envelope.go` (+45), `forward.go`
  (+17), `registry.go` (+10), `push_wake.go` (new, 160 lines), and
  `cmd/pyrycode-relay/main.go` (+15). No `log_allowlist.go` change — every
  new log call site uses only `server_id` / `binary_conn_id` / `err`, all
  already allowlisted.
- `Envelope.PushWake` is `json.RawMessage` with `omitempty`, matching
  `CloseCode`'s (#119) precedent as a relay-interpreted control field kept
  raw at the envelope layer. `Unmarshal` takes the wake branch only when
  `conn_id` is absent/empty/null **and** `push_wake` is present and
  non-null (`hasFrame`'s presence rule, reused).
- `parsePushWake` (`envelope.go`) is the one place that decodes and
  validates the wake object — `platform == "fcm"` (rejects `apns` and
  anything else), non-empty `token`. Its decoder-failure error is bare
  `ErrMalformedPushWake`, not a wrapped `json.Unmarshal` error, so no input
  fragment reaches error text.
- `PushWaker.Request` is the forwarder's single entry point: nil receiver
  (push off) → `ErrPushOff`; structural validation; then, under one mutex,
  admission against the per-server-id `IPRateLimiter` and a buffered-channel
  in-flight cap. Admitted wakes spawn one goroutine against the waker's own
  `context.Context` (not the binary connection's), so a wake requested just
  before a binary disconnects still completes.
- `Registry.pushWaker *PushWaker` + `SetPushWaker` follow the existing
  "set once at boot, nil = off" shape `SetForwarderHooks` established.
  `StartBinaryForwarder` reads `reg.pushWaker` directly — no interface or
  extra forwarder parameter.

## Patterns established / reinforced

- **Second relay-interpreted control field on `Envelope`, same shape as the
  first.** `PushWake json.RawMessage` sits alongside `CloseCode uint16`
  (#119) — both stay untyped/raw at the envelope layer so a `conn_id`
  envelope carrying either field (even malformed) decodes exactly as before
  either field existed. Any future relay-addressed control field should
  follow the same "raw at the boundary, parsed only on its own path" shape.
- **Drop-under-two-independent-limits, never queue, for any future
  relay-originated outbound call triggered by untrusted input.** See
  [ADR-0013](../decisions/0013-push-wake-async-dispatch-bounded-not-verified.md).
- **`IPRateLimiter` is a generic string-keyed primitive, not an
  IP-specific one.** Reused unchanged, keyed on server-id — no new limiter
  type was needed.

## Lessons learned

(From the PR body's Lessons learned section.)

- `Envelope.PushWake` is kept as `json.RawMessage` and is only parsed on the
  wake path. A typed field would have turned a `conn_id` envelope that
  carries a malformed `push_wake` into an unmarshal error, which silently
  changes phone routing.
- The registry holds a concrete `*PushWaker`, not an interface. A nil
  pointer then means push is off, with no typed-nil-interface trap when
  `main` has no credentials.

## Security review

Architect self-review (builder, #133): PASS, one SHOULD FIX addressed before
merge — admission must be atomic with `Close` so `wg.Add` never races
`wg.Wait` and `IPRateLimiter.Allow` is never called after
`IPRateLimiter.Close`; the shipped code holds `w.mu` across the whole
admission sequence (closed-check, rate-limit check, slot acquire, `wg.Add`),
and a test drives `Close` against a blocked send to cover it. Full findings
in [`docs/specs/architecture/133-push-wake-dispatch.md`](../../specs/architecture/133-push-wake-dispatch.md#security-review).

The review explicitly accepted, as a residual (not a defect), that the relay
cannot verify a claimed device token belongs to the claiming binary's own
phones — see [ADR-0013](../decisions/0013-push-wake-async-dispatch-bounded-not-verified.md)
and [`docs/threat-model.md` § Outbound network calls](../../threat-model.md#outbound-network-calls--fcm-push-wake).

## Out of scope

- APNs (iOS push).
- Telling the daemon a device token is dead; retry policy.
- A metric on dropped/refused wakes — the residual abuse risk above is not
  currently observable without reading logs.
- A global wakes-per-second ceiling beyond the per-server-id rate and the
  relay-wide in-flight cap — revisit if abuse across many server-ids is
  observed.
