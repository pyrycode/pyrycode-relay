# Ticket #115 — Stop counting a gracing binary in `Counts()`

`Registry.Counts()` returned `len(r.binaries)`, which kept counting a binary as connected for its whole grace window after it disconnected (`ScheduleReleaseServer` armed, entry not yet reclaimed or expired). `/healthz`'s `connected_binaries` and the `pyrycode_relay_connected_binaries` gauge both read `Counts()`, so both over-counted for up to the grace duration. LOW-severity finding from the 2026-07-03 cross-repo code review.

## Implementation

- `Counts()` (`internal/relay/registry.go`) now subtracts, under the existing `RLock`, every server-id present in both `r.binaries` and `r.timers`. A timer armed for an unheld id (e.g. `ScheduleReleaseServer` called against a slot nobody holds) is not subtracted — only the intersection counts.
- No new type, field, or lock. `reclaim`/`takeover` already delete the timer entry in `replaceBinaryLocked`, so a binary counts again the instant it reclaims its slot; expiry deletes both entries together, so the post-expiry state needed no change.
- Phones are unaffected — a gracing binary's phones are still counted (they stay connected through the binary's grace window; see [`connection-registry.md`](../features/connection-registry.md)).
- `BinaryFor`, `Snapshot`, and routing are untouched: the gracing entry still exists for them, only `Counts()`'s definition of "connected" narrowed.
- Neither `/healthz` (`healthz.go`) nor the metrics collector (`metrics_connections.go`) needed edits — both are thin readers of `Counts()`.

## Patterns established

- No new pattern; this is a one-function, same-lock guard on an existing getter. The verifier's pass note: the correctness argument is representation-based — a server-id can only appear in both `r.binaries` and `r.timers` if a live claim preceded the timer (fresh claims require no pending timer; reclaim/takeover clear the timer atomically with the swap), so intersection membership *is* "disconnected and gracing," not an approximation.

## Documentation handoff

- [`connection-registry.md`](../features/connection-registry.md) § API and § Invariants — `Counts()`'s doc-comment and the invariants list now state that a binary in its grace window is excluded, its phones are not.
- [`connection-count-gauges.md`](../features/connection-count-gauges.md) — the gauge description and the `pyrycode_relay_connected_binaries` line now state the same exclusion, since the gauge is a pull-based reader of `Counts()` with zero code changes of its own.

## Lessons learned

- The verifier flagged a non-blocking NIT: `metrics_connections.go`'s `NewConnectionsMetrics` help string for `pyrycode_relay_connected_binaries` ("binary connections currently held by the relay registry") is still literally true but doesn't mention the grace-window exclusion. Left as-is per the verifier ("does not block the merge... next time someone edits this file") — no code change was warranted for a passing gate's NIT, and the doc-only fix belongs with whichever future ticket next touches that file's help strings.

## Testing

`TestCounts_ExcludesGracingBinary` (`internal/relay/registry_test.go`) covers: two claimed binaries with a phone on one → `(2,1)`; a timer on an unheld id doesn't lower the count; `ScheduleReleaseServer` on the held id → `(1,1)`; reclaim via `ClaimServer` → `(2,0)` (phones evicted per #127); a second `ScheduleReleaseServer` + `TakeoverServer` on the other id → `(2,0)` again. The pre-existing `TestClaimServer_ReclaimDuringGrace_EvictsPhonesWith4404`'s `(2,1)` expectation is unchanged. `go test -race ./internal/relay/...`, `go vet ./...`, and the build all pass.
