# Ticket #154 — Bound the phone outbox by bytes, not frames

`phoneOutboxDepth = 16` counted frames, on the premise that the queue only fills once the kernel send buffer for that phone is already full. That premise broke at connect time: a `pyry` daemon's six connect-time reconciles (`reconcileModals`, `reconcileQuestions`, `reconcileQueues`, `reconcileModelLists`, `reconcileSlashCommandLists`, `reconcileBackgroundTaskRosters`) each send one small frame per session, so a daemon holding a dozen or more sessions produces well over 16 frames, read off the binary socket in a few TCP reads and enqueued in microseconds — before the phone's `run` goroutine has written more than one or two. The 17th frame overflowed the queue and closed a healthy phone with `1011`, flaking five mobile live-e2e tests on every redial for up to a minute. What #113 actually protected was memory (16 × 256 KiB = 4 MiB per phone), so the bound now charges that figure directly, in bytes.

## Implementation

- `internal/relay/phone_outbox.go`: the frame-count channel (`items chan outboxItem`, capacity `phoneOutboxDepth`) became a mutex-guarded FIFO slice (`queue []outboxItem`) plus a byte counter (`queued int`) and a capacity-1 wake-up channel (`ready chan struct{}`, never closed — same "late `Enqueue` can't panic" reasoning the old `items` channel had). New constants: `phoneOutboxBudget = 4 << 20` (4 MiB) and `outboxItemOverhead = 64`. `itemCost(frame) = len(frame) + outboxItemOverhead` is what one queued item charges.
- `Enqueue` now computes `cost := itemCost(frame)` and, under `mu`, accepts the item only if `queued + cost <= budget`; on acceptance it appends to `queue`, adds `cost` to `queued`, unlocks, then does a non-blocking send on `ready`. The lock is held only for the slice append and int add — never across conn I/O. Overflow behaviour (mark `done`, async `closeWithCode` guarded by `doneOnce`, `ErrPhoneBacklogFull`) is unchanged.
- `run` waits on `done` or `ready`, then pops items one at a time via a new `next()` helper (pops `queue[0]` under `mu`, zeroes the vacated slot, resets `queue` to `nil` once empty so the backing array doesn't grow unbounded) and calls `deliver` outside the lock. **The item's cost is subtracted only after `deliver` returns** — the frame being written stays charged against the budget for the whole write, which is why the max-size-frame worst case (15 items) is one fewer than before (16 queued + 1 in flight), not larger.
- `newPhoneOutbox`'s third parameter renamed `depth int` → `budget int`. `ClientHandler` (`client_endpoint.go`) passes `phoneOutboxBudget` instead of `phoneOutboxDepth`.
- `cmd/pyrycode-relay/main.go`: the `defaultMaxConnections` derivation comment's `phoneOutboxDepth × maxFrameBytes = 16 × 256 KiB = 4 MiB` line rewritten to name `phoneOutboxBudget` directly; the 4 MiB figure and the cap of 20 are unchanged (ticket AC3).
- `internal/relay/server_endpoint_test.go`: the stalled-phone conflict-probe test's comment (naming `phoneOutboxDepth`) updated to `phoneOutboxBudget`.
- Tests (`phone_outbox_test.go`): two new tests — `TestPhoneOutbox_Burst_DeliveredInOrder` (AC1: 300 distinct 1 KiB frames enqueued back to back against a stalled phone, all accepted, delivered in order on release, no close) and `TestPhoneOutbox_StalledPhone_BoundedBytes` (AC2: table over max-size and 1 KiB frames against a never-released stalled phone — accepted bytes never exceed the budget, phone closes `1011`, pending frames dropped, later `Enqueue` returns `ErrPhoneOutboxClosed`; the small-frame case also asserts more than 300 frames accepted, which a frame-count bound would fail). `TestPhoneOutbox_BacklogFull_Closes1011` re-expressed with a budget sized in `itemCost` units instead of a literal depth of 2. `stallPhone.Send`'s `entered` signal changed from a blocking send to a non-blocking one with a `default` branch, since its old 64-slot buffer would otherwise wedge (not fail) a 300-write test.

## Patterns established

- **Charge the in-flight item, not just the pending ones, when a budget is meant to bound everything the structure pins.** The old frame-count channel implicitly excluded the item `run` was actively writing from the "queue full" check (it had already left the channel). The byte-budget rework charges `itemCost` until `deliver` returns, so the budget genuinely bounds "bytes this outbox could be holding at any instant," not just "bytes waiting to be sent." Worth reusing wherever a bound is meant to model total exposure rather than backlog depth.
- **A per-item overhead charge closes the gap a byte-only budget would open.** Charging only `len(frame)` would let a hostile daemon queue up to `budget` bytes' worth of near-empty frames — i.e., an effectively unbounded item count, each with its own goroutine-scheduling and slice-growth cost. `outboxItemOverhead = 64` bounds the count independently of size (≤ `budget / overhead` = 65536 items here), the same shape as charging a minimum cost per unit in any resource-budget design.

## Lessons learned

- **A test harness's own bounded buffer can silently cap the scenario it's meant to exercise.** `stallPhone.Send`'s `entered` channel had capacity 64; a test enqueuing 300 frames didn't fail — it hung, because the 65th blocking send never got a reader. The fix (non-blocking send, `default` drop) matters generally: a synchronization channel used purely as a "something happened" signal should almost always be non-blocking, since its buffer size is an implementation detail of the harness, not a property under test.
- **Whether an overflow's close code survives to the binary's close notice is unconfirmed.** `phoneCloseCode` (`client_endpoint.go`) maps whatever error `StartPhoneForwarder`'s read loop sees to the close notice sent to the binary — the phone's own WS status if present, else `1001`. Whether a relay-initiated `1011` (from an outbox overflow) actually surfaces as `1011` to that read loop, or as a status-less error that falls back to `1001`, was not traced end to end during this ticket. Recorded in [`phone-outbox.md`](../features/phone-outbox.md) as an open question rather than guessed at.
