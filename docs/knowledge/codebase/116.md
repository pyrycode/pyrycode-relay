# Ticket #116 — Avoid a full phone-snapshot alloc and linear scan on every forwarded frame

`StartBinaryForwarder` resolved each envelope's `conn_id` by calling `Registry.PhonesFor(serverID)`, which allocates and copies a fresh slice of every phone for that server-id, then scans it — one allocation per forwarded frame, and GC pressure on a 256 MB Fly machine under binary-driven load.

## Implementation

- New `func (r *Registry) PhoneFor(serverID, connID string) (Conn, bool)` in `internal/relay/registry.go`, placed next to `BinaryFor`. Takes `r.mu.RLock`, ranges over the live `r.phones[serverID]` slice, returns the first `Conn` whose `ConnID()` equals `connID`, or `(nil, false)` for an unknown server-id or conn_id. Allocates nothing.
- `StartBinaryForwarder` (`internal/relay/forward.go`) replaces its `PhonesFor` scan loop with `phone, ok := reg.PhoneFor(serverID, env.ConnID)`; the `!ok` branch still takes the existing `binary_forwarder_unknown_conn_id` log-and-continue path, unchanged.
- No conn_id index was added. The scan is bounded by the per-server-id phone cap (`maxPhones` = 16, `cmd/pyrycode-relay/main.go`), so a linear scan is cheap; an index would need to stay in sync across the register, unregister, reclaim-eviction, and grace-expiry paths for no measured benefit.
- `PhonesFor` is untouched and stays for its other callers (broadcast-style fan-out, tests).
- Returning the `Conn` after the read lock releases has the same lifetime semantics as an element of the old `PhonesFor` snapshot — the phone may be unregistered concurrently, and the forwarder already tolerates that through `Enqueue`/`Send` errors.

## Patterns established

- `BinaryFor` was already the one-method, zero-alloc, RLock-scan accessor pattern for a single binary lookup; `PhoneFor` is the same shape for a single phone lookup by `(serverID, connID)`. A future single-item lookup on the registry should follow this shape rather than reaching for `PhonesFor` + a manual loop.

## Testing

New tests in `internal/relay/registry_test.go`:

- `TestPhoneFor_FindsRegisteredPhone` — two phones registered under one server-id, each conn_id resolves to its own `Conn`; an unknown conn_id and an unknown server-id both return `(nil, false)`.
- `TestPhoneFor_ZeroAllocs` — `testing.AllocsPerRun` over a hit and a miss (100 iterations, not `t.Parallel()` since `AllocsPerRun` counts process-wide mallocs) asserts 0 allocations.

`forward_test.go` needed no edits — the existing forwarder suite, including the unknown-conn_id log-and-continue case, exercises `StartBinaryForwarder` through its public behaviour and passed unchanged. `make check` (`go vet` + `go test -race`) is clean.
