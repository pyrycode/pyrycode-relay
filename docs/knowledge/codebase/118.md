# Ticket #118 — configure a Fly health check for the relay

`fly.toml` gained a `[[services.tcp_checks]]` block on the `internal_port = 8080` service and `[deploy] strategy` switched from `"immediate"` to `"rolling"`, so a relay that refuses to boot now fails `flyctl deploy` instead of silently leaving production down. Pure config change — no Go code, no new dependency, one file touched (~25 lines). Filed from the 2026-07-03 Cross-Repo Code Review: the boot-refusal specs (#77, #79, #81) claimed a misconfiguration "fails the deploy's health check", which wasn't true — there was no check, and `immediate` doesn't wait for checks even when one exists.

## Implementation

- **`fly.toml` (+21/-4)** — `[[services.tcp_checks]]` added under the `internal_port = 8080` service (`grace_period = "30s"`, `interval = "15s"`, `timeout = "5s"`), with a comment explaining why the check is TCP and on 8080 rather than HTTP on either port. The `internal_port = 8443` service gets no check. `[deploy] strategy` changed `"immediate"` → `"rolling"`, with its comment rewritten to say rolling waits for checks while immediate doesn't, and that rolling never creates a second machine on this one-machine fleet. `max_unavailable = 1` and every other line unchanged.

## Why TCP on 8080, not HTTP on either port

No port a Fly check can reach serves `/healthz` today:

- 8080 404s everything except the ACME HTTP-01 challenge ([ADR-0002](../decisions/0002-autocert-explicit-failure-on-port-80.md)) — there's no `/healthz` route here to probe with HTTP, but a bare TCP connect proves the listener is up.
- 8443 requires a PROXY protocol v2 header before the TLS handshake even starts ([`NewProxyProtoListener`](../features/proxy-protocol-listener.md), #110). Fly's checker connects directly with no such header, so any probe — TCP or HTTP — fails in the TLS handshake path. That server has no `ErrorLog` set, so a TCP check there would log a line to stderr on every failed probe (every 15s, forever) — pure noise, since the check can never pass.
- Checking 8080 still covers 443: a boot refusal exits before either listener binds, and `runServers` drains and exits if any listener fails, so both ports go down together. One check is sufficient signal for both.

Serving `/healthz` on a reachable new surface would be a new public endpoint and a threat-model re-review — explicitly out of scope; see [`docs/security-followups.md` § *`/healthz` exposure*](../../security-followups.md).

## Why `rolling`, not `immediate`

Fly's configuration reference: `immediate` "replaces all Machines without waiting for health checks"; `rolling` replaces Machines one at a time and waits for each one's checks. The `fly.toml` comment this ticket replaced called rolling "inapplicable" on a single-machine fleet — wrong, because rolling still updates the one machine in place and creates no second machine, so the single-instance invariant ([`docs/architecture.md` § *Single-instance constraint*](../../architecture.md)) is untouched. `max_unavailable = 1` was already redundant-but-documents-intent on a one-machine fleet and needed no change.

## Risk accepted

A spurious check failure removes port 80 (ACME HTTP-01 + the ADR-0002 404 fallback) from Fly's proxy on this single-machine fleet — mitigated by generous timings (boot is local-only and sub-second on shared-cpu-1x / 256 MB, so 30s grace is roughly a 30× margin). Port 443 has no check, so a spurious 8080 failure doesn't take the WebSocket surface offline. A TCP check only proves the socket accepts, not full liveness — a wedged process whose kernel backlog still completes handshakes would still pass; a deeper probe needs an HTTP endpoint Fly can reach, which is the same out-of-scope new-surface trade-off as `/healthz` above.

## Security review

Self-reviewed by the builder (PASS) — the check opens and closes a TCP connection with no request sent, so no header/envelope/payload reaches any handler; content-blindness, credentials, subprocess argv, and TLS paths are all untouched. Full findings in [`docs/specs/architecture/118-fly-health-check.md`](../../specs/architecture/118-fly-health-check.md).

## Documentation handoff — satisfied

- [`docs/knowledge/features/fly-deploy.md`](../features/fly-deploy.md) — `[deploy] strategy` table row and operator-direct deploy bullet now say `rolling`; new § *Deploy health check* describes the TCP check and why it's TCP-on-8080.
- [`docs/deploy.md`](../../deploy.md) — steady-state deploy step 2 now says `rolling` and that the deploy fails if the machine never passes its check, with a link to the feature-doc rationale.
- [`docs/security-followups.md`](../../security-followups.md) § *`/healthz` exposure* — notes Fly's check is TCP on 8080, not an HTTP probe of `/healthz`, so the "breaks Fly health probes" caveat no longer applies to that endpoint.

## Out of scope (deferred)

- **HTTP `/healthz` reachable by a Fly check.** Would need a new public-facing surface (bind on a port Fly's checker can reach without a PROXY header) and a threat-model re-review. Tracked in `docs/security-followups.md` § *`/healthz` exposure*.
- **Deeper liveness probing beyond "socket accepts".** A TCP check can't distinguish a healthy process from one wedged but still completing handshakes from its kernel backlog.
