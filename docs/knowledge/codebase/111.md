# Ticket #111 — Per-message read deadline on `WSConn.Read`

`WSConn.Read` (`internal/relay/ws_conn.go`) now bounds receipt of one complete inbound message to `readMessageTimeout` (30s), armed only once the message's first data-frame header arrives. Closes a real gap: `docs/threat-model.md` § *DoS resistance* had credited this to "per-frame deadlines (#15)", but #15 only ever added the **write** timeout on `Send` — nothing bounded a peer that starts a message and then dribbles or stalls it while still answering heartbeat pings. The heartbeat proves liveness, not progress.

## Implementation

- `Read(ctx)` derives `msgCtx, cancel := context.WithCancel(ctx)` and calls `w.conn.Reader(msgCtx)` — the wait for the first data-frame header is still bounded only by the caller's `ctx`, so idle connections are untouched. Once `Reader` returns, `time.AfterFunc(w.readTimeout, cancel)` arms (stopped on return via `defer`), and `io.ReadAll(r)` reads the rest. If the peer hasn't delivered the whole message (payload plus any continuation frames) before the timer fires, the library closes the connection and `Read` returns a non-nil error — the forwarders' existing exit/cleanup path (`internal/relay/forward.go`) runs unchanged, since they already treat any `Read` error as "log `*_read_end`, return."
- This is the pattern `coder/websocket`'s own `Conn.Reader` doc comment prescribes: the context passed to `Reader` binds the *entire* message (including continuation frames, per `msgReader`), and cannot be swapped mid-message, so a deadline has to be a timer that cancels that same context after the header arrives.
- New field `readTimeout time.Duration` on `WSConn`, set from the new `readMessageTimeout` constant in `NewWSConn`. It exists purely so same-package tests can shorten the deadline on one connection (`testReadTimeout = 500ms`) without a package-level var that would race across parallel tests; production never writes it post-construction.
- No signature changes anywhere — `Read`'s callers, `phoneSource`/`binarySource`, are unaffected. No new sentinel error: the deadline surfaces as `context.Canceled` (possibly wrapped), and the forwarders don't branch on error kind.
- Full design and file-read list: `docs/specs/architecture/111-per-message-read-deadline.md`.

## Patterns established / reinforced

- Second instance (after `writeTimeout` on `Send`) of "policy constant lives next to the mechanism it bounds, in `ws_conn.go`" rather than at a wiring site — appropriate here because, unlike `drainDeadline` or the rate-limit policy block, there's only one call site and no operator-facing knob.
- Confirms the existing "test-only field shortcut" shape: an unexported struct field mirrors a constant so tests can vary it per-instance without a constructor parameter or exported setter (`readTimeout` next to `NewWSConn`'s existing pattern for other test-adjustable internals in this package).

## Lessons learned

- `coder/websocket` buffers a **non-final** data frame and only flushes it to the wire on the connection's *next* final-frame or control-frame write. The fragmented-message stall test (`TestWSConn_Read_StalledFragmentedMessage_ClosesWithinDeadline`) therefore doesn't see the stalled bytes arrive at the moment the peer calls `Writer.Write` — it arrives when the peer answers its first ping (a control frame), which is the next flush. The architecture spec didn't anticipate this; the test's ping cadence (two pings, spaced `testReadTimeout/4` apart, each with a `testReadTimeout/2` budget) exists to give this flush-on-pong behavior room under `-race` without the test becoming flaky. Anyone adding a similar "peer stalls mid-message but must still look alive" test against this library should budget for the flush being deferred to the next control-frame write, not assume it happens the instant `Write` is called.
- The dribbled-frame test (`TestWSConn_Read_DribbledFrame_ClosesWithinDeadline`) needed a hand-rolled WebSocket peer over a hijacked `net.Conn` because `coder/websocket`'s own client/server API has no way to emit a genuinely partial frame (one byte at a time) — the library always buffers and flushes complete writes. When a test needs sub-frame granularity against this library, hand-rolling the wire bytes (as `startEcho`'s sibling helper does here) is the only route; there's no library knob for it.
- Deadline value in tests settled at 500ms (not the ~300ms the spec sketched) specifically so the two mid-stall pings in the fragmented test have margin under `-race`, which slows goroutine scheduling. Any future test against a similarly short deadline in this package should default to ≥500ms rather than reaching for the shortest value that passes locally.
