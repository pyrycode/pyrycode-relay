# Ticket #112 — Probe an unresponsive incumbent on a server-id conflict

A `/v1/server` claim that conflicts with a held `serverID` no longer closes straight to `4409`. It first pings the incumbent for up to `conflictProbeTimeout` (10s). An incumbent that answers keeps the slot, exactly as before. One that doesn't — the common shape of a crash-restarted daemon whose predecessor dropped silently (power loss, NAT timeout, no FIN/RST) — is taken over immediately, instead of making the new claim wait up to 60s for the heartbeat to notice. This closes the gap the ticket named: phones were routing to a dead conn for up to a minute while the restarted daemon retried into `4409`.

## Implementation

- `internal/relay/registry.go`: new `Registry.TakeoverServer(serverID string, incumbent, conn Conn) error` — identity-scoped (refuses if `binaries[serverID]` is held by anything other than `incumbent` at lock time), reaching the exact reclaim semantics `ClaimServer`'s grace branch already had (cancel pending timer, swap binary, evict phones with `reclaimCloseCode`/`4404` outside the lock). Both paths now share one implementation, `replaceBinaryLocked`, extracted in this ticket — there is exactly one reclaim behaviour in the codebase, not two that must be kept in sync.
- New `Registry.ScheduleReleaseServerIfHeld(serverID string, conn Conn, d time.Duration) bool` — `ScheduleReleaseServer` scoped to a specific conn, sharing an `armGraceLocked` helper with the unscoped original. `ScheduleReleaseServer` itself is untouched (18 call sites across 5 test files; nothing in production calls it after this ticket).
- `internal/relay/server_endpoint.go`: `ServerHandler`'s exported signature is unchanged (9 call sites); it now delegates to an unexported `serverHandler(reg, logger, grace, probeTimeout, maxFrameBytes, metrics)` so tests can shrink `probeTimeout`. On `ErrServerIDConflict`, the handler calls `takeoverUnresponsive`, which reads the incumbent via `BinaryFor`, pings it through a narrow `pinger` interface (`Ping(ctx) error`, satisfied by `*WSConn`) under `context.WithTimeout(r.Context(), probeTimeout)`, and:
  - answers or isn't a `pinger` (test fakes only) → `ErrServerIDConflict`, unchanged 4409 path;
  - request context ends first (shutdown) → propagates that error, no log, same as any other shutdown teardown;
  - times out → `TakeoverServer`, then `go closeWithCode(incumbent, websocket.StatusInternalError, "heartbeat timeout")` — the exact code/reason the heartbeat itself would eventually send, borrowed rather than invented.
- The disconnect defer now calls `ScheduleReleaseServerIfHeld(serverID, wsconn, grace)` instead of the unscoped call. This is the hazard the ticket named explicitly: a displaced incumbent's handler still runs its own disconnect defer after losing the slot, and the unscoped call would arm a timer whose 30s-later expiry deletes the *new* binary. The existing pointer-identity stale-fire guard in `handleGraceExpiry` needed no change — every swap of `binaries[serverID]` already deletes the pending timer under the same lock via `replaceBinaryLocked`, so an expiry can never fire against a slot it doesn't recognize.
- `conflictProbeTimeout = 10 * time.Second` is a package constant, not threaded as policy through `main.go` the way `grace` is. It's derived from an internal bound (`WSConn`'s `writeTimeout`), not from the wire protocol, so it doesn't belong at the wiring site.

## Patterns established

- **A second entry point into existing reclaim semantics is a shared-helper extraction, not a copy.** `replaceBinaryLocked` is the reusable pattern here: when two trigger conditions (grace-timer-pending vs. probe-confirmed-dead) should produce identical state transitions, factor the transition itself out rather than duplicating it or collapsing the two triggers into one check.
- **Scope a "release/cleanup on my way out" call to the caller's own identity when a handler's teardown can run after its resource has been reassigned.** `ScheduleReleaseServerIfHeld`'s `cur != conn` check is the general shape: any defer that mutates shared state on cleanup needs to reconfirm it still owns that state if another actor could have taken it over first.
- **Borrow an existing close code/reason instead of inventing one when the semantic meaning is identical.** The probe's timeout is closed with the heartbeat's own `1011 "heartbeat timeout"` rather than a new code, because from the wire's perspective it's the same event arriving sooner.

## Lessons learned

- A live incumbent's pong is only read between its forwarder's frames, and `phone.Send` is synchronous with a 10s `writeTimeout`. Any probe timeout of 10s or less can therefore, in principle, displace a live binary stalled on a slow phone — this is why the probe uses the ticket's stated ceiling rather than "a few seconds," and why the residual risk (issue #140) was filed rather than designed around inline: decoupling pong handling from the forwarder's phone sends needs its own design (e.g. per-phone bounded send queues), not a one-line change riding along with this ticket.
