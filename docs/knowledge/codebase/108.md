# Ticket #108 — `WSConn.Send` writes WebSocket text frames, not binary

`WSConn.Send` wrote `websocket.MessageBinary`, but every other component on the
wire uses **text** frames: the mobile client (`OkHttpRelayTransport`) closes the
connection with `StatusUnsupportedData` on the relay's *first* forwarded binary
frame, the daemon transport (`internal/transport/wssclient.go`) writes text, and
the Go test doubles (`fakerelay`/`fakephone`) write text. The relay was the sole
non-conformant component. The fix is a single outbound-opcode literal flip to
`websocket.MessageText`, plus a doc-comment that brings the `Send` contract in
line with the authoritative wire spec, plus one regression test that pins the
opcode at the `Send` boundary.

The wire is **always text**: the relay forwards the routing envelope as UTF-8
JSON with ciphertext base64-encoded inside the `data` field
(`pyrycode/pyrycode/docs/protocol-mobile.md:195`); it never sees raw ciphertext.
The original report's "Decision needed: text or binary" resolves to text with no
genuine choice and no spec change — `protocol-mobile.md:302` § *Encoding* already
mandates "line-delimited JSON over WS text frames … UTF-8." First real phone to
connect end-to-end; exactly the class of bug the emulator e2e rung exists to
catch.

## Implementation

- **Production — one literal (`internal/relay/ws_conn.go:84`).**
  `w.conn.Write(ctx, websocket.MessageBinary, msg)` →
  `w.conn.Write(ctx, websocket.MessageText, msg)`. `MessageText` is already
  exported from the imported `github.com/coder/websocket` (no import churn). The
  context, write-deadline, `writeMu` serialisation, and `closeOnce` cancellation
  are untouched — the opcode is a pure argument value.
- **Production — doc comment (`ws_conn.go:71-78`).** Rewritten so it no longer
  calls the frame "binary": it states `Send` writes a single **text** frame and
  cites `protocol-mobile.md § Encoding` (line-delimited JSON over WS text frames,
  UTF-8) and the mobile client's close-on-binary behaviour. The serialisation /
  write-deadline / "any non-nil return ⇒ drop the connection" sentences are
  preserved verbatim. The word "binary" now survives only in `Read`'s comment
  ("binary vs text … discarded"), which stays accurate — inbound is unaffected
  because `Read` already discards the message type.
- **Test — `TestWSConn_Send_UsesTextOpcode` (`internal/relay/ws_conn_test.go`).**
  Stands up its **own** `httptest` peer that captures the observed
  `websocket.MessageType` onto a buffered (cap-1) channel, dials it, wraps the
  dialed client in `NewWSConn(client, "test-conn-id", 256*1024)`, calls `Send`
  once, and asserts the captured type `== websocket.MessageText` **and**
  `!= websocket.MessageBinary` (the second assertion's failure message names the
  #108 regression directly). 2s `time.After` timeout; handler goroutine exits
  after one read under deferred `srv.Close`/`wc.Close`.
- **Blast radius — confirmed two callers only.** `forward.go:66` (binary leg,
  forwards a relay-`json.Marshal`ed envelope) and `forward.go:154` (phone leg,
  forwards `env.Frame`) are the *only* production callers of `Send`. Both peers
  expect text, so the change is direction-consistent across both legs. No other
  outbound WS frame write exists in production (`healthz.go:55` is an HTTP body
  write, not a WS frame).

## Patterns established

- **Test the real opcode with a dedicated peer, don't retrofit the shared
  helper.** `startEcho` (the helper for 6 existing `ws_conn_test.go` tests)
  deliberately discards the inbound message type. Rather than thread a
  type-capture channel through it — which would cascade into all 6 call sites —
  the new test stands up its own minimal peer. Adding the regression guard cost
  zero edits to existing tests. The same "new behaviour gets a new self-contained
  test fixture rather than a parameter cascade through a shared helper" shape
  recurs across the relay's test suite.
- **Confirmed RED before GREEN.** The new test was verified to fail against the
  pre-fix `MessageBinary` literal before the opcode was flipped (PR #109
  Testing), so it genuinely guards the regression rather than passing
  vacuously.
- **The doc comment is the contract surface.** The `Send` comment now cites the
  authoritative wire spec by file and section. When a single literal carries a
  cross-repo protocol obligation, the obligation lives in the doc comment at the
  call boundary, not only in an external spec.

## Lessons learned

- **All-text fakes structurally cannot catch a wrong-opcode bug.** The
  fakerelay/fakephone wire tests stayed green for the entire life of this bug
  because the fakes also write text — no relay-repo test ever observed the
  relay's *actual* outbound opcode. A test that mirrors the production opcode by
  construction cannot detect a divergence in that same opcode. The deterministic
  guard had to be a peer that captures the raw `websocket.MessageType`
  independently of any fake. This is the belt-and-suspenders "different fabric"
  rule applied to test doubles: when the fixture and the code-under-test share
  the same assumption, the fixture verifies nothing about that assumption.
- **The first real-peer connection is where wire-conformance bugs surface.** Every
  in-repo component agreed on text, so the divergence was invisible until a real
  phone (which enforces the close-on-binary rule) connected through the emulator
  e2e (rung 3): `phone_registered` then immediately
  `phone_forwarder_read_end err="unexpected binary frame"`. In-repo tests that
  only exercise relay↔fake paths cannot substitute for the emulator rung when the
  bug is a mismatch against an out-of-repo peer's strictness.

## Security

`security-sensitive`; architect self-review **PASS** (spec
`108-ws-text-frames.md § Security review`), re-confirmed by code review (PR #109).
The one opcode-specific risk — RFC 6455 text frames must carry valid UTF-8,
whereas binary frames carry arbitrary bytes — is **not reachable**: both `Send`
inputs are relay-validated UTF-8 JSON (the binary leg forwards a
relay-`Marshal`ed envelope; the phone leg forwards `env.Frame`, which passed the
envelope boundary's JSON well-formedness check, and JSON is UTF-8 by spec). No
path forwards arbitrary attacker bytes through `Send`. Even in the hypothetical
where the library rejected a malformed text write, `Send`'s contract is "non-nil
⇒ drop this one connection" — a single contained drop on a stateless relay, never
relay-wide. The inbound `SetReadLimit` cap and the slow-loris `writeTimeout` are
untouched. The change *reduces* divergence from the threat-model's wire spec.
