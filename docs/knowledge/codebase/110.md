# Ticket #110 — Parse Fly PROXY protocol v2 on the HTTPS listener

Behind Fly's raw-TCP services the relay saw Fly's edge proxy as the socket
peer, so the per-IP rate limiter put every client — one attacker, and every
reconnecting daemon/phone after a deploy — in one bucket. Adds
`--https-proxy-protocol` (off by default): with it set, the autocert HTTPS
listener requires a PROXY protocol v2 header before the TLS handshake and
uses its source address as `RemoteAddr`, so `ClientIP` and the rate limiter
key on the real client IP with zero changes to either. `fly.toml` enables
Fly's `proxy_proto` handler (v2) on the external `443` port and passes the
new flag.

See [feature doc](../features/proxy-protocol-listener.md) for the full
design and [ADR-0012](../decisions/0012-go-proxyproto-for-proxy-header-parsing.md)
for the dependency choice.

## Implementation

- New `internal/relay/proxyproto.go` (63 lines) + `proxyproto_test.go` (259
  lines); `cmd/pyrycode-relay/main.go` (+40/-10) wires the flag, the mutex
  guard, and the `listen` closure branch; `main_e2e_test.go` (+90) adds the
  mutex-table row and a wiring test; `fly.toml` (+26/-10) and `go.mod` /
  `go.sum` (new `github.com/pires/go-proxyproto v0.15.0`).
- `NewProxyProtoListener(inner net.Listener, headerTimeout time.Duration)`
  wraps `proxyproto.Listener` with an explicit `ConnPolicy: REQUIRE` closure
  (not the library's mutable `DefaultPolicy` global) and a `ValidateHeader`
  that accepts only v2 PROXY-command headers with a `*net.TCPAddr` source —
  see the feature doc for why the library's own defaults weren't enough.
  `headerTimeout <= 0` is a constructor error.
- The `listen` closure for `httpsSrv`: flag off is byte-identical to the
  pre-#110 `s.ListenAndServeTLS("", "")` call; flag on inserts
  `net.Listen` → `NewProxyProtoListener` → `s.ServeTLS(pln, "", "")`. The
  wrapper has to sit *under* `ServeTLS`'s TLS listener, since the PROXY
  header precedes the `ClientHello`.
- `--https-proxy-protocol` joined the existing `fs.Visit`-based
  `--insecure-listen` mutex guard from #96 (same exit-2 shape, extended
  error text).
- `fly.toml`'s `443` port comment was rewritten from "handlers omitted on
  purpose" to name `proxy_proto` as the one handler allowed, and to state
  the handler/flag deploy-together requirement inline (both mismatches fail
  443 closed).

## Patterns established / reinforced

- **Second `_<goos>`-free header-before-payload wrapper.** No new pattern
  name, but this is the first place the relay wraps a `net.Listener` below
  `http.Server` rather than configuring `http.Server` fields directly — a
  precedent for any future pre-HTTP connection-level concern (e.g. a future
  connection-count cap from `docs/security-followups.md`).
  `CheckListenerPorts` ([listener port allowlist](../features/listener-port-allowlist.md))
  needed no change because the bound port is identical; only what wraps the
  raw listener differs.
- **Third application of "ADR before the `go.mod` edit"** (ADR-0008,
  ADR-0011, now [ADR-0012](../decisions/0012-go-proxyproto-for-proxy-header-parsing.md))
  — this time the justification is "maintained parser for adversarial,
  pre-TLS bytes" rather than a build-graph-size argument.
- **Explicit-timeout-value discipline for a fixed policy constant.**
  `proxyHeaderTimeout = 5 * time.Second` lives as a `const` at the top of
  `main.go`, matching the existing `drainDeadline` /
  `rateLimitRefillEvery` policy-values-at-wiring-site convention (#21, #47,
  #60, #79).

## Lessons learned

(From the PR body's "Lessons learned" section.)

- `go-proxyproto`'s `Conn.RemoteAddr()` quietly returns the *socket peer*
  address — not an error — for a syntactically valid `LOCAL`-command header,
  and for a v1 `UNKNOWN` header; reads still succeed in both cases. Relying
  on the library's default `REQUIRE` policy alone would have let those
  connections through under the proxy's own address, silently defeating the
  point of this ticket. A test written only against malformed byte streams
  would have passed without the explicit `ValidateHeader` — the gap only
  shows up against a header that parses *successfully* but names the wrong
  thing.
- The library reads `ReadHeaderTimeout: 0` as its own 10s default and a
  negative duration as "no timeout" — a caller that means "no timeout
  configured, use 0" gets a 10s grace period it didn't ask for instead of an
  error. `NewProxyProtoListener` rejects any `headerTimeout <= 0` explicitly
  rather than inheriting either fallback.

## Out of scope

- Restricting the header to trusted upstreams. Under `REQUIRE`, any TCP peer
  reaching the listener — including another machine on the Fly app's private
  6PN network, bypassing Fly's public edge — can supply a header and pick
  its own rate-limit bucket. Fly does not publish stable proxy IP ranges to
  allowlist against. Logged as a candidate in
  [`docs/security-followups.md`](../../security-followups.md).
- Operator verification that Fly accepts the exact
  `proxy_proto_options = { version = "v2" }` key spelling — the architect's
  spec flagged this as unverifiable offline; the PR names it as a
  post-`flyctl deploy` check, alongside confirming that `rate_limited` log
  lines show public client IPs, not Fly-internal ones.
