# Ticket #136 — de-flake `TestUpgradeMetrics_*_TerminalPaths` under full-package `-race`

Test-only fix, one file (`internal/relay/metrics_upgrade_test.go`), no production changes. `ServerHandler` and `ClientHandler` bump their upgrade counters ([#57](../features/upgrade-and-register-failure-counters.md)) *after* the event the `TerminalPaths` subtests wait on — the registry claim `BinaryFor`/`waitForPhones` observe, or the 4409/4404/4429 close frame the test peer's `Read` returns on. Under full-package `-race` load, a one-shot scrape could land in that window and miss a line (e.g. `{endpoint="server",outcome="accept"} 1`), failing about 1 run in 5 on `main` while passing reliably in isolation.

## Implementation

- New helper `awaitUpgradeCounters(t, h, endpoint, outcomes, kinds)` builds the expected `metric{labels} N` line for every cell of the endpoint's outcome set (`allServerOutcomes` / `allClientOutcomes`) and of `allFailureKinds` — unlisted cells at 0, same shape `assertCounter` already checks — then uses the existing `pollUntil` with a 2s deadline until one scrape body contains every line, and only then runs `assertServerOutcomes`/`assertClientOutcomes` + `assertFailureKinds` unconditionally.
- Poll and assert are separate steps: the poll only waits and reports nothing on timeout, so a genuinely wrong count still fails through the same per-cell `assertCounter` path as before (`t.Errorf` with the scrape body in the message), now after the 2s deadline instead of immediately. No second assertion path was added.
- All seven `httptest.NewServer` subtests (server `accept`, `reject_headers`, `reject_409`; client `accept`, `reject_headers`, `reject_404`, `reject_429`) replaced their `assert*Outcomes` + `assertFailureKinds` pair with one `awaitUpgradeCounters` call. The synchronous `reject_rate_limit` subtests (both endpoints, `ServeHTTP` called directly, no goroutine race) are unchanged.
- Verified: `go test -race -count=1 ./internal/relay/` 20 runs clean (builder) + 6 more (verifier); negative check — temporarily setting `reject_404`'s expected count to 2 failed after ~2.01s naming the missing line with the scrape body, then reverted.

## Patterns established

- **Poll-then-assert-unconditionally, not poll-until-pass.** When a test's wait condition (registry claim, close frame) fires structurally before an async counter increment, wrap the wait in the package's existing `pollUntil` and run the *existing* one-shot assert helper after it regardless of poll outcome — don't fold the assert logic into the poll predicate. This keeps the failure message identical to today's (scrape body via `assertCounter`) and doesn't introduce a distinct pass/fail path for the timeout case.
- Verifier flagged a latent (unreached) `awaitUpgradeCounters` sharp edge as a NIT, not blocking: any `endpoint` argument other than `"client"` falls through to the server outcome set/assert, so a typo'd third value would silently poll 2s and then assert against the wrong cells. All seven call sites pass a literal `"server"`/`"client"`, so it doesn't fire today; left as-is rather than adding an unreached `t.Fatalf` guard for a two-value enum with literal call sites.
