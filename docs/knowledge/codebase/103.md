# Ticket #103 — clear SA4000 false positives in `ratelimit_test.go` (sequential-binding)

Test-only refactor, no behaviour change. `staticcheck ./...` reported 4 SA4000 hits ("identical expressions on the left and right side of the `||` operator") in `internal/relay/ratelimit_test.go` at lines **65**, **83**, **98**, **167** — each the shape `if !l.Allow("a") || !l.Allow("a") {`. They are **false positives**: `IPRateLimiter.Allow` mutates the token bucket (decrements a token) on every call (`internal/relay/ratelimit.go:67`), so the two textually-identical operands are not redundant — staticcheck can't model the side effect. Clearing them removes the last lint noise blocking `staticcheck ./...` from being added to `make check`. This is the downstream step that sibling [#98](98.md) (the `nhooyr.io/websocket` → `coder/websocket` migration that cleared the 36 SA1019 deprecation hits) unblocked.

## Implementation

- At each of the 4 sites, the single `if` over two short-circuited `Allow` calls became two named-variable bindings followed by a boolean test over the bound values:

  ```go
  burst1 := l.Allow("a")
  burst2 := l.Allow("a")
  if !burst1 || !burst2 {
      t.Fatal("burst Allows: got false, want true")
  }
  ```

  Two sequential `Allow` calls, both must return `true` — identical behaviour, distinct operands, no SA4000. **No `//lint:ignore SA4000` directive** anywhere (explicit AC): structural fix over suppression.
- **Per-site variable names (load-bearing):** sites 65 and 83 both live in `TestIPRateLimiter_RefillAfterAdvance` at the same block scope, so they use *distinct* name pairs — `burst1`/`burst2` (line 65, "exhaust the burst") and `refill1`/`refill2` (line 83, "two Allows after 2s advance"). Reusing one pair at both would be a compile error (`no new variables on left side of :=`). Sites 98 (`TestIPRateLimiter_FractionalRefillPreserved`) and 167 (`TestIPRateLimiter_EvictionPreservesActiveBucket`) each reuse `burst1`/`burst2` legally in their own function scopes.
- Every `t.Fatal` message is byte-for-byte unchanged. Test logic, table data, and `t.Parallel()` calls are untouched — pure expression-restructuring at the 4 sites (~8 net lines added).
- **No production code touched** (`ratelimit.go`, `ratelimit_middleware.go` unchanged), no new exported symbols. `ratelimit.go:67` was read only to confirm the side effect that makes these false positives.
- **AC #4 scope grep:** `grep -rn 'Allow.*||.*Allow\|Reject.*||.*Reject' internal/` surfaced exactly the 4 known sites and nothing else (architect pre-ran it; the implementer and code review both re-confirmed 0 matches after the fix) — so the ticket stayed scoped to 4 sites and **no follow-up ticket was filed**.
- **Verification:** `go build ./...`, `go vet ./...`, `go test -race ./internal/relay/...` all pass; `staticcheck ./...` returns **0** SA4000 hits across the repo (lines 65/83/98/167 no longer appear). Code review ([PR #104](https://github.com/pyrycode/pyrycode-relay/pull/104)) passed with **no findings**.

## Patterns established

- **Sequential binding, not `//lint:ignore`, for SA4000 false positives on side-effecting calls.** When two syntactically-identical calls in a boolean expression each mutate state, bind each to a named variable before the test. staticcheck's AST check can't see the side effect, but the bound form has distinct operands so the check clears — and the explicit two-call sequence reads more honestly than the collapsed `||`. Structural and local; avoids a global-rule waiver. The reusable template for any future SA4000 hit of this shape.
- **Same-block-scope binding pairs need distinct names.** Two refactored sites inside one function at the same scope cannot both reuse a single `:=` name pair (the second is `no new variables on left side of :=`). Pick intent-revealing names per site (`burst1`/`burst2` vs `refill1`/`refill2`); names may freely repeat across separate function scopes. A `go build` catches the collision immediately.

## Lessons learned

- **The short-circuit vs always-evaluate difference is unobservable here, so the refactor is genuinely behaviour-preserving.** Replacing `!Allow() || !Allow()` (which short-circuits — the second `Allow` doesn't run if the first returns `false`) with two unconditional bindings changes evaluation only in the *failure* path. But on the failure path the next statement is `t.Fatal`, which terminates the test regardless of the extra token decrement — so nothing downstream can observe it. On the passing path both forms evaluate both `Allow` calls identically. The sequential form arguably expresses "exhaust the burst (consume both tokens)" more faithfully than the short-circuited original.
