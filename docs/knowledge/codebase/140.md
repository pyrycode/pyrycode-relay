# Ticket #140 — Pin that a live binary with a stalled phone survives the conflict probe

Test-only, no production change. [#112](112.md)'s conflict probe reads pongs only while `StartBinaryForwarder` is in `WSConn.Read`; before [#113](113.md), a synchronous `phone.Send` to a stalled phone could hold that read loop past `conflictProbeTimeout`, so a live incumbent could fail the probe and be taken over by a concurrent duplicate claim. #113 removed the cause — the forwarder now only enqueues to [`phoneOutbox`](../features/phone-outbox.md) and never waits on a phone write — but nothing exercised the real pong path while a phone write was actually in flight. This ticket adds that end-to-end proof: `TestServerEndpoint_StalledPhone_LiveIncumbentKeepsSlot` in `internal/relay/server_endpoint_test.go`. It passes on `main` as expected, since #113 already fixed the underlying bug.

## Implementation

- One `httptest` server muxes `/v1/server` (`serverHandler`, 200ms probe timeout, well under the 10s `writeTimeout`, 1 MiB frame cap) and `/v1/client` (`ClientHandler`) onto one registry. The incumbent binary dials and calls `CloseRead`, so it answers pings only by reading, mirroring `TestServerEndpoint_DuplicateClaim_4409`'s precedent for "a live client is one that reads." A real phone dials `/v1/client` and never reads, so its socket buffers fill and stay full.
- The binary sends 256 KiB JSON-string frames addressed to the phone one at a time, waiting after each for `Registry.SetForwarderHooks`' `onBinaryForwarded` hook (an `atomic.Int64` counter) to catch up. The first frame whose write doesn't complete within the poll window is the blocked write. This counter-driven stop condition, not a fixed frame count, is load-bearing — see Lessons learned.
- While that write is blocked, a second `/v1/server` claim for the same server-id is dialed. It must read `4409`; the registry must still hold the incumbent; the write counter must not have advanced past the frame that was blocked when the probe started; and the phone must still be registered — proving the pong that answered the probe ran while a phone write was in flight, not after it drained.
- Cleanup uses `CloseNow()` (not a graceful close) on all three connections, unblocking the stalled phone write on teardown.

## Patterns established

- Nothing new — this ticket follows #112's existing `startServerProbe`/`awaitBinary`/`pollUntil` test helpers and #113's `SetForwarderHooks` observability seam exactly as designed. No architecture or test-infrastructure changes were needed to write this proof, which is itself a mild confirmation that #112/#113's seams were sized correctly for this exact assertion.

## Lessons learned

- Stop the send loop on the `onBinaryForwarded` write counter, not a fixed frame count. Kernel socket buffer sizes vary by OS and autotuning, so a fixed count either never blocks a write (the test can't detect the blocked-write condition it exists to create) or overflows `phoneOutboxDepth` into a `1011` close (the condition under test — a blocked write — never gets to coexist with a live probe). The counter-driven loop guarantees at most one frame is ever queued behind the blocked write, so the outbox is nowhere near its depth limit when the probe runs.
- A mutation check that only fakes `phoneOutbox.Send` proves nothing: `StartBinaryForwarder` reaches the outbox exclusively through `Enqueue`, never `Send`. The test only goes red when `Enqueue` itself is mutated to write synchronously (the pre-#113 forwarder shape) — that's the mutation that actually exercises what the test is pinning.
