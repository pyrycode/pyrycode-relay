# Ticket #117 — Phone forwarder malformed-frame policy: document and pin the teardown

No behaviour change. `StartPhoneForwarder` already ended the loop (and so the connection) on a frame `Marshal` rejects with `ErrInvalidFrameJSON`; `StartBinaryForwarder` already logged and continued on a malformed envelope. This ticket makes that asymmetry legible as a decision, not an accident: doc comments on both functions now state the policy and why they differ, and a new test pins the phone side.

## Implementation

- `StartPhoneForwarder`'s doc comment (`internal/relay/forward.go`) gained a paragraph: a `Marshal` rejection ends the loop and the caller's defer closes the phone, because (a) the bad frame came from that phone, so teardown drops only the sender; (b) it bounds `phone_forwarder_marshal_err` to one warn line per connection from an internet peer, and each reconnect re-passes the upgrade rate limiter; (c) no real client has been observed dropped by an encoding glitch.
- `StartBinaryForwarder`'s existing "does NOT return on per-frame errors" paragraph gained the mirror half: closing a binary on one bad envelope would drop every phone it serves, unlike the phone side where there's only ever one sink.
- New `TestStartPhoneForwarder_NonJSONFrame_TearsDown` in `internal/relay/forward_test.go`: sends one valid frame (proves the pipe works), then a non-JSON frame followed by another valid frame. Asserts the forwarder returns an error satisfying `errors.Is(ErrInvalidFrameJSON)`, the binary received only the one pre-malformed frame, and the trailing valid frame is still unread in the phone's channel — so neither the bad frame nor anything after it reached the binary.

## Patterns established

- A pinning test for pre-existing behaviour can't go red on its first run by construction. Per the code-review verdict, this one was proven capable of failing by temporarily flipping the production `return err` to `continue` and watching it fail, then reverting — rather than relying on the test reading correctly.

## Lessons learned

- A test that pins already-existing behaviour can't go red on its first run; the only way to show it would catch a regression is to mutate the code under test and watch it fail (here, `return err` → `continue`), then revert. The two count assertions (exactly one frame reached the binary; the post-bad-frame frame is still unread on the phone) exist specifically to catch a subtler regression than "did the function return an error" — a loop that still forwards the frame *after* the bad one before exiting some other way.
