# Ticket #127 — close inherited phones with `4404` when a binary reclaims its slot during grace

When a binary reclaims its server-id inside the 30-second grace window, the registry used to hand the phones registered for that slot to the new binary conn untouched (ADR-0006, "phones still attached"). Under Mobile Protocol v2 that strands them: a restarted daemon has no Noise session for the inherited conn ids, answers the phone's next `noise_msg` with a fatal `4421`, and the client stops re-dialling. Observed twice against production on 2026-09-15 (daemon restarts at 18:19 and 20:53 Helsinki time; the desktop client showed "Pairing error - Re-pair" and needed a human restart both times). The fix evicts those phones at reclaim time with close code `4404`, which every client already treats as "relay reachable, daemon absent" and retries.

## Implementation

- **`internal/relay/registry.go` — `ClaimServer` grace branch.** The method now takes the lock without a deferred unlock. On the no-grace path it behaves exactly as before (conflict on a held slot, otherwise claim). On the grace path it stops the timer, replaces the binary conn, snapshots `r.phones[serverID]` and deletes the key, unlocks, then spawns one goroutine per evicted phone calling `closeWithCode(p, reclaimCloseCode, reclaimCloseReason)`. Removal under the lock is what keeps `Counts` and the connected-phones gauge honest before the method returns; closing outside the lock is the registry's standing rule (a close can block on the peer's close handshake).
- **`closeWithCode` helper** (same file). Type-asserts the Conn against the private `gracefulCloser` interface from `shutdown.go` and calls `CloseWithCode`, falling back to plain `Close`. `*WSConn` takes the coded path so the wire carries `4404 "binary reclaimed server-id"`; the narrow `fakeConn` in `registry_test.go` takes `Close`. The `Conn` interface is not widened.
- **`reclaimCloseCode = websocket.StatusCode(4404)`** and **`reclaimCloseReason`** constants sit next to `ClaimServer`. The reason string differs from `/v1/client`'s `"no server with that id"` so logs can tell the two `4404` sources apart.
- **Unchanged by design:** `handleGraceExpiry` including its pointer-identity guard, `ScheduleReleaseServer`, `ReleaseServer`, the no-grace `ClaimServer` path, `server_endpoint.go`, and `client_endpoint.go`. Doc comments on `ClaimServer` and `ScheduleReleaseServer` were updated to describe the eviction.
- **No new metric.** The ticket allowed an optional reclaim-eviction counter following the `SetGraceExpiryHook` pattern. Left out to keep the change to the registry; the `server_claimed` log line plus the phones gauge dropping already make a reclaim visible.

## Tests

- `registry_test.go`
  - `TestClaimServer_ReclaimDuringGrace_EvictsPhonesWith4404`: a code-aware fake (`codedFakeConn`, embeds `fakeConn` and adds `CloseWithCode`) receives `4404`, a narrow `fakeConn` gets plain `Close`, a phone on another server-id is untouched, `PhonesFor` and `Counts` no longer report the evicted phones immediately after `ClaimServer` returns, and a new phone registers against the reclaimed binary.
  - `TestClaimServer_NoGrace_PhonesUntouched`: held slot still returns `ErrServerIDConflict`, and a plain `ReleaseServer` followed by `ClaimServer` leaves orphan phones alone.
  - `TestClaimServer_ReclaimDuringGrace_StaleFireTouchesNothing`: captures the armed `*graceEntry` from `r.timers` before the reclaim and calls `handleGraceExpiry` with it directly, which is the exact goroutine a lost `Stop()` race produces. Asserts the hook does not fire and the new binary and its fresh phone survive.
  - Two existing tests changed meaning: `TestScheduleReleaseServer_ReclaimWithinGrace_NoReleaseFires` now checks the stale fire against a phone registered after the reclaim, and `..._PhoneRegisteredDuringGrace_SurvivesReclaim` became `..._ClosedOnReclaim`.
- `metrics_connections_test.go`: the stale-fire gauge test now expects the phones gauge to drop to 0 at reclaim and registers a fresh phone before the stale-fire wait.
- `cmd/pyrycode-relay/main_e2e_test.go` — `TestRun_ReclaimDuringGraceClosesPhoneWith4404`: boots `run()` on a loopback port, dials binary b1 and a phone, proves the phone is registered by round-tripping a frame to b1, closes b1, dials b2 until the claim sticks (`dialServerUntilClaimed` retries a `4409` because the prior handler's `ScheduleReleaseServer` defer runs a moment after the close handshake completes), asserts the phone's `Read` returns close status `4404`, then re-dials the phone and round-trips a frame to b2. Uses main.go's real 30-second grace, so no timing knob was added.

## Patterns established

- **Eviction at the moment a live peer exists, not at the moment the old one dies.** Closing at release would let a phone re-dial into the closed conn and time out on `noise_resp`. Reclaim is the first point where a re-dial can succeed, so that is where the close belongs.
- **Reuse a close code the clients already classify.** `4404` was chosen over IANA `1012` Service Restart purely because every client already retries `4404`. A semantically nicer code that no client handles is a new fatal path.
- **Deterministic stale-fire test.** Capturing the `*graceEntry` under the lock and calling `handleGraceExpiry` directly replaces sleep-based races for the pointer-identity guard.

## Out of scope / follow-ups

- The wire spec's close-code table in the pyrycode repo (`docs/protocol-mobile.md`) should gain a sentence on its `4404` row: the relay also sends it to phones evicted by a binary reclaim. Not touched here; noted in the PR.
- Daemon-side backstop: answer a `noise_msg` on an unknown conn with a retryable close instead of `4421`.
- Desktop-side backstop: bound `4421` on an already-authenticated session the way the daemon bounds `4409`.
- Optional reclaim-eviction counter, nil-safe hook shape as `SetGraceExpiryHook`.
