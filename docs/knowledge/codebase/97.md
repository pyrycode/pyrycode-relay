# Ticket #97 — capture fly.toml gotchas surfaced by first deploy bootstrap

Documents the two `fly.toml` requirements that the 2026-05-24 first-deploy bootstrap of `pyrycode-relay` surfaced as `flyctl deploy` failures, and encodes both in the checked-in manifest so the next deploy (and the eventual `pyryco.de` re-cutover when DENIC delegation lands) doesn't re-discover them from error messages. Docs + config only — no production code, no tests.

## Implementation

- **`fly.toml` (+7)** — new top-level `[env]` table placed directly under the single-machine-cap header comment block (`fly.toml:19-22`) carrying `PYRYCODE_RELAY_SINGLE_INSTANCE = "1"` plus a two-line inline rationale that ties the env var to the #65 self-check (so a future reader doesn't delete it as dead config). And one new line — `processes = ["app"]` — as the first line inside each of the two existing `[[services]]` blocks (`fly.toml:43`, `fly.toml:57`). No other edits to `fly.toml`; the `[processes]`, `[build]`, `[[mounts]]`, `[[vm]]`, `[deploy]` blocks are untouched, no reordering, no comment rewrites elsewhere.
- **`docs/deploy.md` (+26)** — new `## fly.toml gotchas` subsection placed between *One-time bootstrap* and *Steady-state flow* (`docs/deploy.md:43-67`). Three numbered items: (1) the `PYRYCODE_RELAY_SINGLE_INSTANCE` env-var requirement with a one-line link to `docs/architecture.md § The PYRYCODE_RELAY_SINGLE_INSTANCE bypass` (no duplicated explanation — the architecture doc is canonical); (2) the `processes = ["app"]` per-`[[services]]` requirement with a one-line rationale tying it to the Fly schema rule + distroless-has-no-shell argv constraint that makes `[processes]` always defined; (3) a forward pointer to [#96](https://github.com/pyrycode/pyrycode-relay/issues/96) noting that the `internal_port = 80` / `internal_port = 443` pinning is provisional and that the high-port pattern (`8080`/`8443` mapped to external `80`/`443`) should be documented as the canonical Fly recipe once #96 ships.

No code changes. No new exported symbols. No edits to `internal/relay/`. No edits to `docs/architecture.md` (the existing § *The PYRYCODE_RELAY_SINGLE_INSTANCE bypass* anchor is what `docs/deploy.md` now links to).

## Patterns established

- **Co-locate substrate config with its in-binary explanation.** The pre-#97 manifest treated `PYRYCODE_RELAY_SINGLE_INSTANCE` as something the operator would discover at first-boot failure. #97 moves the assertion into the manifest under a header comment that names the #65 self-check by issue number. Future substrate flags that exist to satisfy an in-binary check should follow the same shape: declare the flag in `fly.toml` with a comment naming the ticket / sentinel that consumes it, and add the gotcha to `docs/deploy.md` so the operator-facing surface and the manifest surface agree. The opposite — encoding substrate quirks into the manifest with no co-located explanation — is the same anti-pattern that #95 fixed by narrowing `ErrCacheDirInsecure` (see [codebase note #95](95.md) "scoped exception beats workaround that encodes substrate quirks").
- **`docs/deploy.md` "gotchas" subsection is the canonical home for fly.toml-schema requirements that aren't self-evident from the file.** Placement is between *One-time bootstrap* and *Steady-state flow* because the audience is an operator editing the manifest (first bootstrap, re-cutover, porting to a new app) — not the operator running the steady-state deploy. A future fly.toml requirement that surfaces as a `flyctl deploy` validation error or boot-time refusal belongs in this subsection as a new numbered item.
- **Forward pointer in deploy doc as a documented-follow-up shape.** Item (3) in the gotchas section is the load-bearing structural choice. The high-port recipe was deliberately NOT pre-written here (the spec said "that belongs in the doc PR that ships alongside #96") and the forward pointer carries the operator instruction without committing to a specific shape. When a sibling ticket adds an operator-configurable knob, the deploy doc's pointer to it is the seam that keeps the doc edit out of the sibling's PR while making the follow-up impossible to forget. Same shape applies to any future "this section will change once X ships" — leave a pointer with the issue number as a clickable link, then revise in the X-shipped doc PR.
- **Per-`[[services]]` `processes = ["app"]` is non-negotiable once `[processes]` is defined.** And `[processes]` is always defined here because distroless has no shell to expand env vars into argv (see [codebase note #38](38.md) § "Argv, not shell"). A future ticket that adds a third `[[services]]` block (e.g. for a metrics port exposed beyond loopback — though #60 deliberately bound metrics to `127.0.0.1`) MUST add `processes = ["app"]` as the first line. `flyctl config validate` is the structural backstop, but a CI deploy that fails at validate is a slower feedback loop than getting the line right at PR time.

## Lessons learned

- **First-deploy bootstrap surfaces requirements that are invisible in the spec and invisible in the manifest until you hit them.** Both gotchas (the env var, the per-service process mapping) were not in `docs/deploy.md`, not in `fly.toml`, and not in the original #38 Fly-deploy ticket. They surfaced only because an operator ran `flyctl deploy --remote-only` against a real Fly account and read the error messages. The general lesson: when shipping a deploy manifest for a new substrate, the first real deploy IS the spec — file the gotchas as a follow-up ticket immediately, even if they look one-line-trivial, because the institutional knowledge evaporates within days of the bootstrap session ending. The session log (`Second Brain/📋 Projects/2026-04-10 - Pyrycode/Session Logs/2026-05-24.md`) was load-bearing for filing #97 cleanly two days later.
- **`processes = ["app"]` is a Fly schema requirement when `[processes]` is defined — not a stylistic recommendation.** The validation error `Service has no processes set but app has 1 processes defined; update fly.toml to set processes for each service` is unambiguous, but only if you've already seen it once. The mapping looks redundant on a single-process app (there's only one process, why name it on every service?), and the temptation is to treat the warning as a tutorial-grade nag. It is not — `flyctl deploy` refuses the manifest, the deploy never reaches the rolling-release stage. The Fly docs cover this, but the Fly docs are large and the schema rule is buried; encoding the rule in `docs/deploy.md` + the in-repo manifest is the institutional-knowledge backstop.
- **The forward pointer to #96 is the right call even though #96 shipped on the same day.** Sibling #96 (configurable autocert listener addresses) merged into `main` immediately before this PR — see [codebase note #96](96.md). The temptation was to fold the high-port recipe into #97 since the prerequisite had landed. The spec held the line: "do not pre-write the high-port recipe — that belongs in the doc PR that ships alongside #96." Honouring the boundary means the high-port recipe lands in its own focused PR (with operator verification against a real Fly deploy, per #96 AC5) rather than being a side-quest of the gotchas-documentation PR. The general principle: even when two prerequisites land in the same merge window, the documentation seams between them are worth preserving — they keep PR review focused and they keep the lessons-learned section of each PR scoped to one thing.
- **Architecture-doc anchor links require a slug check.** The gotchas item (1) links to `architecture.md#the-pyrycode_relay_single_instance-bypass`. GitHub's auto-slugger lowercases, strips backticks, and turns underscores into… underscores (not hyphens — but spaces become hyphens). The resulting slug for the heading `### The \`PYRYCODE_RELAY_SINGLE_INSTANCE\` bypass` is `the-pyrycode_relay_single_instance-bypass`, NOT `the-pyrycode-relay-single-instance-bypass`. Mistaking the underscore→hyphen rule (which applies to spaces in title text, not to literal underscores in code-backtick spans) would produce a broken intra-doc anchor that renders fine but doesn't jump. The spec called this out as the load-bearing AC; the developer's defence is to click the link in the PR preview before merging.
