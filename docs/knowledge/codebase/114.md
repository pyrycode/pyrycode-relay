# Ticket #114 — Global live-connection cap before accept

The per-IP rate limiter (#47) bounds the *rate* of upgrade attempts, not the number of *live* connections. An attacker staying under the refill rate could add connections without bound until the 256 MB Fly machine OOMs. This ticket adds one global cap, shared by `/v1/server` and `/v1/client`, that closes that path. The per-IP concurrency cap stays deferred.

## Implementation

- New `internal/relay/conncap.go`: `ConnCap` wraps a buffered channel (`slots`) sized by `NewConnCap(max int, logger)`; `max <= 0` returns an error wrapping `ErrInvalidConnCap`. `Wrap(next http.Handler) http.Handler` does a non-blocking try-acquire (`select` with a `default` branch) before `next` runs — full channel means an empty-body `503`, one `logger.Warn("conn_cap_reached", "path", r.URL.Path, "remote", remoteHost(r))` line, and `next` never runs, so `websocket.Accept` never runs either. A successful acquire `defer`s the release, so the slot frees on every exit from `next`, panic included. `inUse()` (unexported, `len(slots)`) exists only for tests.
- `cmd/pyrycode-relay/main.go`: new `--max-connections` flag (default `defaultMaxConnections = 20`), `relay.NewConnCap` called right after the insecure-listen mutex guard — a non-positive value logs `refusing to start: invalid --max-connections` and returns exit 2, same shape as the other boot-time refusals. One `connCap` instance wraps both endpoints, placed *inside* the rate limiter: `upgradeMetrics.WrapServerRateLimitDeny(rateLimit(connCap.Wrap(relay.ServerHandler(...))))` and the client equivalent. That ordering means a rate-limited request never takes a slot, and `WrapServerRateLimitDeny` / `WrapClientRateLimitDeny` still see only HTTP 429 — the cap's 503 never reaches those counters.
- The `defaultMaxConnections` comment derives the value the same way the `maxFrameBytes` comment does: per-connection cost ≈ 4.4 MiB (3 goroutine stacks ≈ 24 KiB; websocket/bufio/TLS buffers ≈ 64 KiB; a full 16-frame `phoneOutboxDepth` backlog at `maxFrameBytes` = 4 MiB; one in-flight `maxFrameBytes` read = 256 KiB), reserving ~56 MiB of the 256 MB machine for the binary/runtime/autocert/kernel buffers, and accounting for `GOGC=100`'s ~2× live-heap headroom with no `GOMEMLIMIT` set. Rounds ~22 down to 20. At that default, the production `fly.toml` command needs no change.
- Tests: `internal/relay/conncap_test.go` — construction validation; an over-cap unit test asserting the sentinel handler ran exactly once, the 503 status, exactly one `conn_cap_reached` log line, and that two distinctive header values never appear in the log; and `TestConnCap_SharedSlotReleasedOnEveryExit`, which runs the real `ServerHandler` + `ClientHandler` behind one shared `ConnCap` and covers three release paths — normal phone close, a reject-after-accept 4404 (no binary present), and a phone torn down when its binary's grace period expires — each confirming `inUse()` returns to the expected count and a fresh upgrade then succeeds at the boundary. `cmd/pyrycode-relay/main_e2e_test.go` adds `TestRun_MaxConnectionsNonPositiveRefusesStart` (0 and -1 → exit 2) and `TestRun_ConnCapGatesUpgradesNotHealthz` (cap of 1, a live binary holds the slot, both upgrade routes answer 503, `/healthz` still answers 200).
- Docs updated: [`threat-model.md`](../../threat-model.md) § DoS resistance, [`security-followups.md`](../../security-followups.md) ("Slowloris connection-count cap" now shipped, "Per-IP concurrent connection cap" narrowed), new [`connection-cap.md`](../features/connection-cap.md) feature doc, [`rate-limit-middleware.md`](../features/rate-limit-middleware.md) § Out of scope.

## Patterns established

- **A slot taken before the handler runs, released by `defer` when it returns, covers every close path for free** — no need to enumerate close reasons at the call site. This works here for the same reason it works for `pushWakeMaxInFlight` (#133): both `ServerHandler` and `ClientHandler` stay inside `ServeHTTP` for the connection's whole life and return only after their own cleanup, so a slot taken on entry and released via `defer` on return outlives every per-connection goroutine without the wrapper needing to know about heartbeat timeout, grace expiry, or any of the reject-after-accept close codes individually.
- **A cap-style middleware composes *inside* an existing status-code observer, not outside it.** `connCap.Wrap` sits inside `rateLimit`, which sits inside `WrapServerRateLimitDeny`/`WrapClientRateLimitDeny` (#57's HTTP-429-only observers). Nesting a new deny path inside an existing narrow-purpose observer (rather than wrapping it, or teaching it a second status code) keeps that observer's contract — "counts only 429" — true without an edit to `metrics_upgrade.go`.

## Lessons learned

- The default sized for the worst case (20) equals the rate limiter's burst (20), so one IP can fill the whole global cap in one burst and lock out new upgrades while existing connections keep working. That trade is better than an OOM crash loop, but it makes the deferred per-IP concurrency cap the next DoS gap to close — recorded in `security-followups.md` rather than treated as a defect in this ticket, since the alternative (sizing the cap well above the burst) would have meant either shrinking the burst or accepting a larger per-connection memory budget than the 256 MB machine supports.
