# Ticket #150 — Log FCM's error reason when a wake send fails

`FCMSender.Send` (`internal/relay/push.go`) previously drained a non-2xx FCM
reply and returned only the HTTP status. On 2026-09-24 every wake to project
`pyrycode-mobile` came back `status 404`, from both an ATD and a Play
emulator, and the log couldn't say whether that was `UNREGISTERED`, a
project mismatch or something else (pyrycode/pyrycode-mobile#955). This
ticket names FCM's own reason without risking free text or the device token
reaching the log.

## Implementation

- The discard-drain became a bounded read (`io.LimitReader`, still
  `fcmMaxDrainBytes` = 4 KiB) into memory; the 2xx path still discards it.
- On a non-2xx reply, `fcmErrorReason` decodes that buffer into the new
  unexported `fcmErrorReply` struct, which declares only `error.status` and
  `error.details[].{@type, errorCode}` — `error.message` has no field, so
  FCM's free text is never held in a typed value. `errorCode` is taken only
  from a detail whose `@type` is `fcmErrorType`
  (`type.googleapis.com/google.firebase.fcm.v1.FcmError`).
- `isFCMEnum` (1–64 bytes of `[A-Z0-9_]`) gates both values before they're
  used, so a hostile or misconfigured-proxy reply that echoed request data
  into those fields still can't reach the error string.
- `ErrFCMSend: status 404 (NOT_FOUND, UNREGISTERED)` when both are present,
  one alone in the parens when only one is, and unchanged
  `ErrFCMSend: status N` for an empty/non-JSON/field-less/decode-failed body
  — a decode failure is never wrapped or reported.
- `PushWaker.send`'s comment updated (no code change there): the error
  carries the HTTP status plus FCM's enum reason codes, never the token or
  free text. No new log key — the reason travels inside the already
  allowlisted `err` value under `push_wake_send_failed`.

## Patterns established

- Decoding an upstream reply into a struct that simply omits the free-text
  field (rather than decoding everything and then redacting) makes "nothing
  else from the body" a compile-time property of the type, not a runtime
  discipline — the pattern `parseFCMCredentials` already uses for rejecting
  credential values without echoing them, now applied to a reply body
  instead of a request input.
- Gating extracted upstream values through a narrow shape check
  (`isFCMEnum`) before they reach an error/log string is a reusable move
  wherever a value nominally "off content path" still isn't fully trusted —
  this is Google's reply to the relay's own outbound request, not a routed
  payload, so it wasn't a content-blindness question, but it also isn't
  fully trusted input.
